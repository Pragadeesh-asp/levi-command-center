# Architecture

## Product identity and current implementation

LEVI COMMAND CENTER (tagline: “Your Personal AI Operations Headquarters”) is a local-first Windows desktop application built with Tauri 2, React 19, strict TypeScript, Vite, and Tailwind CSS 4. Rust owns desktop integration. SQLite remains the source of truth for user-created operational data. The existing Tauri identifier `com.local.claude-command-center` and database file `command-center.db` are intentionally preserved for compatibility.

The product is organized around Operations (accounts, browsers/profiles, later projects/tasks/deliverables), Intelligence (future LEVI AI), and Control (future reminders, activity, analytics, and automation). Phase 2 currently implements browser and account management only; later modules remain planned.

## Runtime boundaries

- **Frontend (`src/`)**: presentation, navigation, form validation, and database-backed account/profile views. It does not read browser profile files or launch processes directly.
- **Tauri host (`src-tauri/`)**: narrow OS-facing commands detect browser installs/profiles, validate registered paths, and launch a requested account using safe argument vectors, never shell strings.
- **Persistence (`src-tauri/migrations/`)**: versioned SQL migrations. The database is `sqlite:command-center.db` in Tauri's app data directory. The SQL plugin applies registered migrations on connection load.
- **Notifications**: persistent reminder rows are authoritative. On startup and while running, a Rust scheduler checks due rows and dispatches OS notifications; notification scheduling is recoverable from SQLite after restarts.
- **Activity**: explicit user actions and known system events are logged with a source field. Browser presence is not evidence that an AI account is working.

## Folder structure

```text
src/                    React application and design system
src-tauri/              Tauri host, permissions, Rust integration, migrations
  capabilities/         Least-privilege window permissions
  migrations/            Versioned SQLite migrations
docs/                   Architecture, schema, roadmap, status
```

Future modules should be grouped by feature (`accounts/`, `projects/`, `tasks/`, etc.) with shared UI primitives in `components/` and repository/data access in `lib/db/`. Avoid a single global component or untyped data bag.

## Key decisions

1. An account references a browser profile. Many accounts can reference the same profile only where that is an intentional mapping; profiles themselves are independent of accounts and their paths are unique within a browser.
2. Projects and accounts are many-to-many through `project_accounts`; tasks have optional project and account links to preserve records when an owner is removed.
3. Records are archived where historical context matters. Foreign-key deletion is restrictive for browsers and profiles, cascading only for dependent assignment/history rows, and `SET NULL` for history-facing task links.
4. UUID-like text IDs are generated by the application. Timestamps use UTC ISO-8601 values.
5. Browser configuration is never edited by the app. It stores executable/profile paths and launches the chosen browser with its documented profile selector. Before launch, known Chromium `Singleton*` and Firefox parent-lock markers cause a warning/error; the app never removes lock markers, edits profile databases, copies cookies, or terminates browser processes. This conservative marker check cannot reliably establish process ownership or guarantee safe reuse when no marker is present.
6. Phase 2 interfaces use SQLite records; no sample account or synthetic dashboard metrics are presented as real data.
7. Browser registration and launch never read or alter cookies, passwords, tokens, or browser databases. Removing a registration does not delete its profile directory.

## Future LEVI AI architecture (planned, not implemented)

LEVI — Command Intelligence will be provider-independent and will only receive approved application context after the operational data model is stable. The planned backend boundary is:

```text
Conversation Manager → AI Orchestrator → Provider Interface
                                      ├─ FreeLLMAPI adapter (default)
                                      └─ OpenRouter adapter (manual/fallback)
                         Model Registry · Usage Tracker · policy/audit layer
```

Adapters must be written only after reviewing the providers’ current primary documentation. No endpoint, authentication format, model identifier, quota, or token allowance is assumed here. The frontend will talk only to the trusted Tauri/Rust backend; credentials will use Windows OS-backed secret storage and never enter React, browser storage, frontend environment variables, or logs. Requests will exclude browser credentials and unnecessary personal data.

The planned permission model has read access, confirmed actions with visible parameters, and explicitly authorized automation. The action layer will restrict tools, require confirmation for sensitive/destructive actions, maintain an audit trail, and allow automation to be disabled. No AI request, chat simulation, provider adapter, or autonomous system/browser control is part of Phase 2.

## Security posture

The current capability grants only core window, SQL, and notification plugin permissions. It does not grant filesystem, shell, or process permissions to the webview. Future browser launch and file-open behavior must be implemented as narrow Rust commands with validation and explicit confirmation where relevant. No cookies, passwords, or tokens are collected or copied.

## Phase 2.1 verification boundary

The Tauri development binary and visible window were verified on Windows. The dashboard and Accounts/Browser Profiles navigation rendered. Live UI verification covered account save, profile remapping, SQLite activity, manual registration of an isolated temporary profile directory, and restart persistence. Rust integration coverage verifies transaction rollback in a temporary SQLite database. The Brave executable version was displayed after Rescan. Real-browser launch/error behavior and the remaining browser version labels remain unverified; see `KNOWN_ISSUES.md`.

## Build prerequisites

Frontend: Node.js/npm. Native Windows build: Rust stable toolchain and Cargo, Microsoft C++ Build Tools (MSVC), and WebView2 Runtime. Phase 1.1 native Windows verification passed; Phase 2 native verification is tracked in `PROGRESS.md`.
