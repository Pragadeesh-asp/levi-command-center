# Architecture

## Product identity and current implementation

LEVI COMMAND CENTER is the central operations application in **LEVI ECOSYSTEM**, whose tagline is “Your AI Workforce. Your Projects. Your Intelligence.” The ecosystem also plans LEVI BROWSER and LEVI — COMMAND INTELLIGENCE; neither is implemented. The current Command Center is a local-first Windows desktop application built with Tauri 2, React 19, strict TypeScript, Vite, and Tailwind CSS 4. Rust owns desktop integration. SQLite remains the source of truth for user-created operational data. The existing Tauri identifier `com.local.claude-command-center` and database file `command-center.db` are intentionally preserved for compatibility.

The product direction is organized around Operations (accounts, browsers/profiles, projects and tasks), Intelligence (future LEVI AI), and Control (workforce status, reminders, activity and analytics). Project/task CRUD, transactional worker eligibility, dependency-aware queue assignment, project-scoped file claims, a local-record Workforce Center, a manual usage-limit/checkpoint workflow, and the persistent reminder scheduler are implemented. Live OS toast delivery still needs Windows verification; live AI remains unimplemented. See `ROADMAP.md` for current boundaries.

## Runtime boundaries

- **Frontend (`src/`)**: presentation, navigation, form validation, database-backed project/task lists and queue controls, and account/profile views. It does not read browser profile files or launch processes directly.
- **Tauri host (`src-tauri/`)**: narrow commands own account/browser operations and transactional project/task mutations, queue assignment, dependency validation and file claims. Assignment changes, claim acquisition/release, task history and activity records are committed atomically. Browser launches use safe argument vectors, never shell strings.
- **Persistence (`src-tauri/migrations/`)**: versioned SQL migrations. The database is `sqlite:command-center.db` in Tauri's app data directory. The SQL plugin applies registered migrations on connection load.
- **Notifications**: the Rust scheduler and Reminders UI use the Tauri notification plugin. Delivery is user-opt-in and persisted; Windows toast delivery and permission-denial behavior are not yet verified. Scheduling runs only while the app is open, with overdue catch-up after restart.
- **Activity**: account and project/task mutations log explicit events; task field changes are transactionally coupled to `task_history`. Browser presence is not evidence that an AI account is working.

## Folder structure

```text
src/                    React application and design system
src-tauri/              Tauri host, permissions, Rust integration, migrations
  capabilities/         Least-privilege window permissions
  migrations/            Versioned SQLite migrations
docs/                   Architecture, schema, roadmap, status
```

Future modules should be grouped by feature (`accounts/`, `projects/`, `tasks/`, etc.) with shared UI primitives in `components/` and repository/data access in `lib/db/`. Avoid a single global component or untyped data bag.

## Key decisions

1. An account references a browser profile. Many accounts can reference the same profile only where that is an intentional mapping; profiles themselves are independent of accounts and their paths are unique within a browser.
2. Projects and accounts are many-to-many through `project_accounts`; tasks have optional project and account links to preserve records when an owner is removed.
3. Records are archived where historical context matters. Foreign-key deletion is restrictive for browsers and profiles, cascading only for dependent assignment/history rows, and `SET NULL` for history-facing task links.
4. UUID-like text IDs are generated by the application. Timestamps use UTC ISO-8601 values.
5. Browser configuration is never edited by the app. It stores executable/profile paths and launches the chosen browser with its profile selector. On Windows, the launch guard compares running processes by executable and readable command-line profile arguments. A verified matching Chromium user-data directory and profile may be reused by invoking the same executable with that exact profile; an ambiguous profile, same storage root with a different profile, unreadable command line, or matching Firefox profile is blocked with a close-and-retry warning. Known Chromium `Singleton*` and Firefox parent-lock markers also block launching unless an exact Chromium session match was established. A process snapshot and lock marker cannot eliminate races or prove profile ownership in all cases. LEVI never removes lock markers, edits profile databases, copies cookies, or terminates browser processes.
6. Launch commands report executable/profile validation, conflict-check result, process-start PID and executable path, and requested URL. The UI labels the result `unknown` because process creation does not confirm a visible browser window or completed navigation. Account activity records a process-start request rather than claiming that a browser opened. Test launches serialize at the UI and require manual close acknowledgement before the next test.
7. Phase 2 interfaces use SQLite records; no sample account or synthetic dashboard metrics are presented as real data.
8. Browser registration and launch never read or alter cookies, passwords, tokens, or browser databases. Removing a registration does not delete its profile directory.

## Future LEVI AI architecture (planned, not implemented)

LEVI — Command Intelligence will be provider-independent and will only receive approved application context after the operational data model is stable. The planned backend boundary is:

```text
Conversation Manager → AI Orchestrator → Provider Interface
                                      ├─ FreeLLMAPI adapter (default)
                                      └─ OpenRouter adapter (manual/fallback)
                         Model Registry · Usage Tracker · policy/audit layer
```

Adapters must be written only after reviewing the providers’ current primary documentation. No endpoint, authentication format, model identifier, quota, or token allowance is assumed here. The frontend will talk only to the trusted Tauri/Rust backend; credentials will use Windows OS-backed secret storage and never enter React, browser storage, frontend environment variables, or logs. Requests will exclude browser credentials and unnecessary personal data.

The planned permission model has read access, confirmed actions with visible parameters, and explicitly authorized automation. The action layer will restrict tools, require confirmation for sensitive/destructive actions, maintain an audit trail, and allow automation to be disabled. API keys must use Windows credential storage and never enter frontend code, web storage, Git or logs. No AI request, chat simulation, provider adapter, or autonomous system/browser control is part of Phase 2.

## Future LEVI BROWSER architecture evaluation (planned, not implemented)

Two candidate designs require a measured comparison before a decision:

| Candidate | Potential advantages | Costs and open questions |
| --- | --- | --- |
| Embedded Tauri/WebView2 with an independent environment and user-data directory per AI Space | Fits the existing Windows/Tauri stack; can provide explicit storage partitioning and Command Center integration | Memory/CPU per environment, WebView2 process sharing, login compatibility, process lifetime, startup and switching performance must be measured. Separate directories alone are not evidence of complete storage isolation. |
| Separate browser processes with dedicated profile directories | Reuses mature browser session, storage and navigation behavior; process boundary is visible | More process/resource overhead, browser-specific contention rules and updates, command-line interoperability, and lifecycle handling. The current app only registers external profiles; it is not LEVI BROWSER. |

Measure RAM per active Space, CPU, background process behavior, session persistence/isolation, startup, switching and concurrent sessions on representative Windows hardware. Do not assume WebView2 is automatically lighter or build a rendering engine. A new migration or implementation choice requires a separate authorized phase.

## Security posture

The current capability grants only core window, SQL, and notification plugin permissions. It does not grant filesystem, shell, or process permissions to the webview. Future browser launch and file-open behavior must be implemented as narrow Rust commands with validation and explicit confirmation where relevant. No cookies, passwords, or tokens are collected or copied.

## Phase 2 verification boundary

The Tauri development binary and visible window were verified on Windows. The dashboard and Accounts/Browser Profiles navigation rendered. Live UI verification covered account save, profile remapping, SQLite activity, manual registration of an isolated temporary profile directory, and restart persistence. Rust integration coverage verifies transaction rollback in a temporary SQLite database. Brave and Chrome executable version resources displayed after Rescan. Phase 2.2 launch, URL, process-contention and window-control evidence is tracked separately in `PROGRESS.md`; do not treat detection or a Claude page opening as authentication success.

## Hybrid permission model (future)

1. **Read:** access approved local records for ordinary questions.
2. **Confirmed action:** present the exact action and parameters before writes or browser opening.
3. **Authorized automation:** execute only actions covered by an explicit, revocable rule; retain action history. Sensitive, destructive and externally consequential actions require confirmation. No unrestricted operating-system access.

## Project usage and time attribution (future)

Usage records will carry source class (API-reported, platform-reported, estimated or manual) plus provider/model/platform/account/project/date and request ID when actually available. Do not invent web-platform tokens, quotas or reset times. Work-session records will attribute project, account and optional task, timestamps, active duration and recording method. Browser-open time is not active-work time. Future project and telemetry entities are concepts in `ROADMAP.md`; migrations are not part of the current stabilization milestone.

## Workforce assignment and manual usage-limit reporting

The project editor manages account membership in `project_accounts`; Rust validates each selected account and commits membership changes with activity records transactionally. Assignment is authoritative in Rust: manual and automatic queue assignment use SQLite `BEGIN IMMEDIATE` transactions to validate active project, account status, browser/profile availability, project membership, dependencies, file claims and competing active tasks, then commit task history and activity together. Browser process presence does not change account availability.

`mark_usage_limited` is a user-reported workflow, not page monitoring. It stores the exact entered message, optional explicitly supplied reset time, checkpoint fields, waiting task/account state, task history, a persistent check-in reminder, and activity atomically. If reset time is blank, it is recorded as unknown and the reminder is scheduled as a one-day manual check-in; that time is not represented as a provider reset. `resume_usage_limited` requires both user-confirmed availability and explicit user authorization, checks browser/profile availability, resolves the pending event/reminder and returns the original task to Ready under the same account in one transaction. No credentials, cookies or page contents are inspected.

The Workforce Center, Task Queue and Reminders screen derive data from SQLite. Optional queue automation polls every ten seconds while the app is open and relies on the same Rust transaction as manual assignment. The reminder scheduler starts after the frontend opens the migrated database, polls every 30 seconds while the app is open, transactionally claims due records and records success/retry state. OS delivery is user opt-in; failed sends retry after five minutes and stale claims recover after ten minutes. Exact-once delivery cannot be guaranteed across a crash between the OS toast and SQLite acknowledgement; a stable notification ID reduces repeat toasts where the platform honors it. Due reminders are checked on restart; there is no closed-app Windows background service. A status such as Working requires the saved account status and an in-progress task; launching a browser alone is not evidence of work.

## Build prerequisites

Frontend: Node.js/npm. Native Windows build: Rust stable toolchain and Cargo, Microsoft C++ Build Tools (MSVC), and WebView2 Runtime. Phase 1.1 native Windows verification passed; Phase 2 native verification is tracked in `PROGRESS.md`.
## Task queue and assignment

Task Queue assignment is validated and committed by the Rust workforce service. Manual queue assignment, automatic next-eligible assignment and task-form assignment share `save_task_transaction`, which uses SQLite `BEGIN IMMEDIATE`, checks project/account/browser/profile/dependency eligibility, claims declared file paths, and records task history/activity atomically. Active file claims are project-scoped, Windows case-folded, separator-normalized and reject path equality plus parent/child overlaps. No filesystem paths are opened or edited by this feature; claims are coordination metadata only. Automatic scheduling is user-controlled and polled by the running Command Center at 10-second intervals. The assigned state is not evidence of external Claude work starting.

Task dependencies are stored as directed edges and checked for self-reference, cycles and same-project membership before save. Incomplete or archived prerequisites block assignment; the queue displays their status and dependency chain. Waiting-for-reset tasks retain their worker and claims until the user-authorized same-account resume flow is used.
