# Architecture

## Phase 1 baseline

Claude Command Center is a Windows 11, local-first Tauri 2 desktop application. The React 19 + TypeScript frontend is bundled with Vite and Tailwind CSS 4. The Rust host owns desktop integration; SQLite is the sole source of truth for user-created work. Zustand is reserved for transient UI state and TanStack Query can coordinate asynchronous data reads once data modules are implemented. The SQL plugin uses bound parameters; UI text is never interpolated into SQL.

## Runtime boundaries

- **Frontend (`src/`)**: presentation, navigation, input validation, view-level state. It must not access browser profile files or launch arbitrary shell commands.
- **Tauri host (`src-tauri/`)**: small, explicit OS-facing command surface. Browser launching will be a Rust command accepting a validated profile/account ID and resolving paths from registered records. It will use argument vectors, never a shell string.
- **Persistence (`src-tauri/migrations/`)**: versioned SQL migrations. The database is `sqlite:command-center.db` in Tauri's app data directory. The SQL plugin applies registered migrations on connection load.
- **Notifications**: persistent reminder rows are authoritative. On startup and while running, a Rust scheduler checks due rows and dispatches OS notifications; notification scheduling is recoverable from SQLite after restarts.
- **Activity**: explicit user actions and known system events are logged with a source field. Browser presence is not evidence that an AI account is working.

## Folder structure

```text
src/                    React application and design system
src-tauri/              Tauri host, permissions, Rust integration, migrations
  capabilities/         Least-privilege window permissions
  migrations/            Versioned SQLite migrations
docs/                   Architecture, schema, roadmap, status
```

Future modules should be grouped by feature (`accounts/`, `projects/`, `tasks/`, etc.) with shared UI primitives in `components/` and repository/data access in `lib/db/`. Avoid a single global component or untyped data bag.

## Key decisions

1. An account references a browser profile. Many accounts can reference the same profile only where that is an intentional mapping; profiles themselves are independent of accounts and their paths are unique within a browser.
2. Projects and accounts are many-to-many through `project_accounts`; tasks have optional project and account links to preserve records when an owner is removed.
3. Records are archived where historical context matters. Foreign-key deletion is restrictive for browsers and profiles, cascading only for dependent assignment/history rows, and `SET NULL` for history-facing task links.
4. UUID-like text IDs are generated by the application. Timestamps use UTC ISO-8601 values.
5. Browser configuration is never edited by the app. It stores executable/profile paths and launches the chosen browser with its documented profile selector.
6. UI navigation in Phase 1 is interactive. Data entry and operational modules are intentionally not represented as finished functionality yet.

## Security posture

The current capability grants only core window, SQL, and notification plugin permissions. It does not grant filesystem, shell, or process permissions to the webview. Future browser launch and file-open behavior must be implemented as narrow Rust commands with validation and explicit confirmation where relevant. No cookies, passwords, or tokens are collected or copied.

## Build prerequisites

Frontend: Node.js/npm. Native Windows build: Rust stable toolchain and Cargo, Microsoft C++ Build Tools (MSVC), and WebView2 Runtime. These were not available in the inspected environment on 2026-11-13, so the native host could not be compiled here.
